# Архитектура «Орбиты»

## Результат и критерии готовности

Два вымышленных студента входят и видят разные учебные данные; могут посмотреть расписание, оценки и новости, отправить заявку и увидеть её сохранённый статус. Сотрудник проводит её до готовности, а владелец получает уведомление и документ. Подмена ID не даёт чужих данных. Все основные действия работают при 360 px.

## Выбор

Один Next.js App Router проект с Node.js runtime. Это позволяет использовать Vercel serverless или standalone-процесс в контейнере/VPS. Отдельный backend и микросервисы не нужны для прототипа. Решение уточняли ECC Architect и GPT-6 Astra с xhigh; серверный код написал Astra xhigh в роли worker.

Поток: браузер → NextAuth cookie → серверная проверка сессии → актуальная роль в БД → CampusService → параметризованные libSQL запросы. React-компонентам передаются только безопасные DTO.

## Границы

- `app/dashboard/layout.tsx`: обязательный вход и первоначальная серверная загрузка данных.
- `components`: интерфейс, формы, контекст текущего студента; не определяет полномочия.
- `lib/auth.ts`, `lib/credentials.ts`: NextAuth JWT в HttpOnly cookie, bcrypt, вход и активность аккаунта.
- `lib/service.ts`: бизнес-правила, владение данными, заявки и уведомления.
- `lib/registration.ts`, `lib/catalog.ts`: регистрация только из вымышленных persona/program; роль и идентификатор назначает сервер.
- `lib/calendar.ts`, `lib/academics.ts`, `lib/schedule.ts`: календарь двух семестров, учебные записи и недельная выборка.
- `lib/teachers.ts`: каталог преподавателей, приватные диалоги, ответы сотрудника и уведомления.
- `lib/db.ts`: ленивое подключение, явная схема, проверка конфигурации.
- `lib/security.ts`, `lib/validation.ts`: same-origin, ограничение JSON, Zod.
- `lib/database-write.ts`: очередь записей одного локального SQLite-клиента; удалённый libSQL использует транзакции провайдера.
- `app/api`: тонкие адаптеры аутентификации, HTTP, ошибок и Cache-Control.
- `scripts/setup-db.ts`, `lib/seed.ts`: явная и повторяемая подготовка БД.

## Хранилище

Таблицы: users, classes, grades, deadlines, requests, request_events, notifications, rate_limits, schema_migrations, user_enrollments, teachers, teacher_threads, teacher_messages. У персональных сущностей есть user_id либо проверяемая связь с обращением владельца; выборки привязаны к actorId. Индексы поддерживают выборки расписания, заявок и переписки.

`getWorkspace` возвращает профиль, текущую неделю и персональные оценки, заявки, уведомления, дедлайны. `/api/schedule?semester=…&week=…` отдельно выдаёт выбранную неделю и причины неучебных дней. В БД заполнены два семестра, но целиком в React-контекст они не отправляются. Списки диалогов ограничены 50, сообщения — последними 100; для длинных сообщений используется content-visibility. Следующий шаг масштабирования — пагинация.

## Жизненный цикл

`submitted → processing → ready`; возможен `submitted/processing → rejected`. Готовые и отклонённые заявки терминальны. Повтор текущего статуса идемпотентен. Статус, история и уведомление записываются одной транзакцией. Готовый документ является демонстрационным HTML, а не официальной справкой или электронной подписью.

## Переносимость

Локально/VPS: файл SQLite на постоянном диске, один процесс приложения. Serverless: внешний libSQL/Turso, учётные данные только на сервере. Нельзя класть рабочую SQLite в ephemeral filesystem функции. Миграция и seed запускаются отдельно от HTTP; cold start не создаёт таблицы и не сбрасывает данные.

Документация библиотек, использованная при планировании: [Next.js](https://nextjs.org/docs/app/getting-started/installation), [NextAuth Credentials](https://next-auth.js.org/providers/credentials), [libSQL](https://docs.turso.tech/sdk/ts/reference).
