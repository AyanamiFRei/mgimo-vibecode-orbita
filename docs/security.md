# Как защищены данные

Пароль сравнивается с bcrypt-хешем (12 раундов в seed). Открытый пароль не хранится в таблице пользователей. Публичный демопароль присутствует в инструкции и seed намеренно: это конкурсные тестовые аккаунты, а не ключ к инфраструктуре.

После входа NextAuth хранит подписанную и зашифрованную JWT-сессию в HttpOnly cookie, с SameSite-защитой и Secure на HTTPS. Срок — 8 часов. Секрет сессии генерируется владельцем и задаётся через `NEXTAUTH_SECRET`. Токен БД и секрет сессии не имеют префикса NEXT_PUBLIC, не передаются компонентам и не включены в исходники.

Сервер повторно читает пользователя, роль и состояние блокировки из БД. Подмена роли в интерфейсе не помогает. Сервис получает actorId из сессии; поле владельца нельзя задать в форме. Студенту доступны только его сущности. Чужая и отсутствующая заявка одинаково дают 404. Студент получает 403 на очередь и операции сотрудника.

Собственные мутации проверяют Origin относительно канонического `NEXTAUTH_URL`, размер JSON и строгую Zod-схему. NextAuth использует собственный CSRF-протокол. Запросы SQL параметризованы. Текст документа экранируется; React экранирует введённые тексты. Готовая справка открывается только после проверки владельца или роли сотрудника, имеет отметку «ОБРАЗЕЦ» и private/no-store.

Лимиты входа и API записываются в БД, поэтому не исчезают при serverless cold start. Транзакции не допускают частичное изменение статуса без истории и уведомления. Неизвестные ошибки возвращают общее сообщение без SQL, стека и паролей. Заголовки запрещают embedding, MIME sniffing, доступ к камере/микрофону и ограничивают источники контента. CSP оставляет inline scripts для Next.js; отдельный nonce-based CSP остаётся возможным усилением, не заявляется реализованным.

Перед публичным запуском нужны HTTPS, постоянная БД и приватные переменные окружения. Для VPS база должна быть доступна только пользователю приложения, а резервные копии — храниться отдельно. Не включайте TRUST_PROXY без reverse proxy, который сам перезаписывает forwarded-заголовки.

Черновик заявки сохраняет только введённые назначение/комментарий в sessionStorage текущей вкладки, ключ разделён по пользователю и типу документа. Секреты и сессионные токены там не хранятся. Черновик удаляется после успешной отправки.

Результаты проверок и честные ограничения записаны в `verification.md`. Прототип не предназначен для настоящих персональных данных и не интегрирован с системами реального вуза.

Регистрация принимает только login/password и перечислимые program/persona. Роль всегда student; ФИО выбирается из вымышленных персонажей, email создаётся в зарезервированном `.example`. Настоящий email, ФИО и служебная роль не принимаются. Почты, SMTP и подтверждения адреса нет по уточнению пользователя. Пароль — от 12 символов и не более 72 UTF-8 байт, чтобы исключить усечение bcrypt. Лимиты регистрации долговечные; занятый логин и конкурентные создания обработаны. Новому студенту создаются собственные учебные записи, пустые заявки и приветственное уведомление.

Диалог преподавателя доступен только владельцу и актуальному сотруднику. Самостоятельно задать user_id/role нельзя. GET не меняет прочитанность; для неё используется отдельный POST. Ответ и уведомление сохраняются транзакционно. Сотрудник отвечает от своего имени; системное сообщение явно помечено демонстрационным. Реальным людям сообщения не отправляются.
